### F01. Условия программ застройщика не попадают в калькулятор

**Django:** при выборе застройщика/ЖК загружает `/mortgage/developer-mortgage-programs/`, учитывает область действия программы и подставляет удорожание, взнос, срок, ставку и льготный период. Предусмотрены восстановление исходных параметров и сообщение о применённой программе.

**React:** загружает только общие `BankProgram` через `/api/v1/mortgage/options/`. Выбор объекта, застройщика или ЖК не вызывает получение условий `DeveloperMortgageProgram`. Наличие отдельного React-справочника программ застройщиков не означает их интеграцию с калькулятором.

На синтетической программе одного и того же банка/ЖК получено:

| Параметр | Django | React |
|---|---:|---:|
| Ставка | 3% | 6% |
| Удорожание | 8% | 0%, остаётся тип «Скидка» |
| Первый взнос | 25% | 20% |
| Срок | 300 месяцев | 360 месяцев |
| Льготный период | 24 месяца под 1% | Не включён |

**Последствие:** одинаковый выбор банка, программы и объекта создаёт разные входные данные и другое предложение клиенту.

Источники: `static/js/mortgage_form.js:740`, `mortgage/views.py:1269`, `api_v1/views.py:651`, `frontend/src/pages/MortgageCalculatorPage.tsx:526`, `:869`.

Исправление: перенести получение и применение условий застройщика, включая приоритет конкретного ЖК и возврат к базовым банковским условиям. Закрепить приведённый сценарий сравнительным тестом.

### F02. Потеряна логика кредитных лимитов

**Django:** выбирает региональный лимит по городу объекта с возвратом к федеральному. При превышении показывает необходимый и дополнительный взнос, льготную/рыночную части и расчётную комбинированную ставку. Рыночная ставка для этого сценария определяется как ключевая ставка + 2 п. п.

**React:** API уже возвращает `creditLimit`, `regionalCreditLimits`, `isPreferential` и `keyRate`, но калькулятор не использует их. Полей региона/города в финансовом запросе и идентификатора программы нет; API рассчитывает переданную ставку без применения кредитного лимита. В Django ограничение также является клиентской подсказкой, поэтому речь именно о потере прежнего сценария и предупреждения, а не о ранее существовавшем серверном запрете.

Воспроизведение: стоимость 5 млн, взнос 20%, льготная программа, кредит 4 млн, федеральный лимит 3 млн и региональный 2 млн. Django показывает предупреждение и варианты; React рассчитывает всю сумму по выбранной льготной ставке без соответствующего блока.

Источники: `static/js/mortgage_form.js:129`, `:337`; `api_v1/views.py:651`; `frontend/src/pages/MortgageCalculatorPage.tsx:311`, `:869`.

Дополнительно различается подстановка обычной программы: Django устанавливает её взнос/срок, React сохраняет больший уже введённый взнос и меньший срок (`Math.max`/`Math.min`). Это изменение поведения нужно явно зафиксировать при восстановлении паритета. Для нулевой банковской ставки React также не повторяет резервный выбор ставки из старого JavaScript.

### F03. Ручной блок объекта стал несохраняемой декорацией

Десять полей — город, район, застройщик, ЖК, корпус, квартира, площадь, планировка, этаж, отделка — присутствуют, но в React это свободные строки `propertyData`. Ни `buildMarketPayload`, ни `buildTrenchPayload` их не отправляют. Изменение любого поля сбрасывает выбранный `propertyId`.

**Django:** использует связанные справочники, каскады и поиск квартиры; валидирует согласованность объекта. При полном ручном заполнении модератор может создать объект вместе с сохранённым расчётом. Для обычного пользователя создание каталожного объекта ограничено ролью — это ограничение не следует снимать.

**React:** после ручного ввода расчёт выполняется только по финансовым параметрам; сохранить его нельзя, даже модератору. При этом текст формы предлагает «заполнить данные вручную». В перехваченном запросе после ввода города нет ни города, ни остальных свойств объекта; кнопок сохранения — 0.

Источники: `mortgage/forms.py:11`, `mortgage/views.py:109`, `:640`, `:1010`; `frontend/src/pages/MortgageCalculatorPage.tsx:311`, `:338`, `:703`, `:931`, `:1090`.

Исправление: вернуть справочные идентификаторы, каскады, проверку и разрешённое ролью сохранение ручного объекта; включать данные в несохранённые экспорты.

### F04. Новый объект связывается со старым финансовым результатом

Воспроизведённая последовательность:

1. Выбрать объект A стоимостью `5 000 000,00`, рассчитать ипотеку.
2. Выбрать объект B стоимостью `5 432 100,67`.
3. Поле стоимости меняется на цену B, прежний результат и кнопка сохранения остаются.
4. Нажать «Сохранить расчёт» без повторного расчёта.

В запросе сохранения получено: **`propertyId` объекта B, но `parameters.propertyCost = "5000000.00"`**. Используется текущий `selectedPropertyIdentifier` вместе с `marketCalculationMutation.variables` от предыдущего запроса. Аналогичная структура есть у траншевого сохранения.

Обычное редактирование финансовых полей тоже оставляет прежний результат на экране без явного признака устаревания. Для самой смены финансовых полей сохранение снимка предыдущего результата может быть осознанным поведением; смешивание этого снимка с новым объектом — подтверждённая ошибка.

Источники: `frontend/src/pages/MortgageCalculatorPage.tsx:712`, `:727`, `:931`, `:985`, `:995`.

Исправление: сохранять объект и параметры единым снимком либо сбрасывать/блокировать сохранение при изменении любого влияющего поля, в том числе объекта.

### F05. Cutover сохраняет строки query-параметров, но теряет их смысл

Старый калькулятор читает `property_id` и `customer`; React — `propertyId` и `customerId`. Middleware оставляет старые имена без преобразования.

Браузером подтверждено: `/mortgage/?property_id=1&customer=4` переходит в `/app/mortgage/?property_id=1&customer=4`, после чего объект и квартира пусты, а клиент не распознаётся. Это затрагивает старые ссылки из Django-карточки объекта, сценарии клиента и сохранённые закладки.

То же относится к фильтрам: старые `filter_*`, `sort_by`, `sort_dir`, а в историях `city`, `cost_from`, `term_from`, `sort`, `order` не переводятся в соответствующий контракт React. Простое сохранение query string при redirect не сохраняет результат отбора.

Источники: `mortgage/views.py:80`, `:693`; `react_frontend/middleware.py:142`; `frontend/src/pages/MortgageCalculatorPage.tsx:435`, `:440`; `templates/property/property_list.html:32`.

Отдельное ограничение отката: при включённом флаге ссылки «Django-версия»/«Прежняя версия» снова перенаправляют в React. Это особенно существенно для предлагаемых интерфейсом обходов неполных справочников и для отсутствующих функций F08/F13. Для реального сравнения и доступа к шаблонам флаг должен быть отключён либо нужен отдельный поддержанный обход redirect.

### F06. Денежные значения теряют копейки

Общий React-форматтер использует `maximumFractionDigits: 0`. Поэтому он округляет не только цену объекта, но и взнос, кредит, переплату, платёж, проценты, основной долг и остаток в графике, кредитные лимиты и финансовый потенциал клиента.

В Django `format_currency` сохраняет два знака; `compact_currency` убирает только нулевые копейки. В API суммы по-прежнему передаются строками с двумя знаками: потеря происходит при отображении в React.

Последствие: экран и Excel/Word могут показывать разные суммы; даже при совпавших расчётах пользователь не может сверить график до копейки. Например, исходные `5 432 100,67` отображаются как `5 432 101 ₽`. Браузером подтверждён платёж: API вернул `23 982,02`, экран показал `23 982 ₽` (`observations.rawPayment` / `displayedPayment` файла доказательств).

Источники: `frontend/src/shared/lib/formatters.ts:1`; `mortgage/utils.py:274`; `mortgage/templatetags/mortgage_filters.py:49`.

Исправление: отдельный денежный формат с двумя знаками для финансовых страниц/графиков; компактное представление допустимо только при сохранении ненулевых копеек.

### F07. Неполные списки выбора и потеря отображения выбранного значения

**Калькулятор:** загружает только первую страницу объектов с `pageSize=100`, без поиска, пагинации или догрузки. При 106+ объектах в списке остаётся 100 вариантов. Прямой `propertyId` за пределами первой страницы загружается отдельным запросом и заполняет сведения, но соответствующего `<option>` нет.

Подтверждено: для объекта вне первой сотни поле квартиры содержит `PARITY-104`, а значение визуального селектора объекта пустое. Пользователь не может выбрать этот объект непосредственно из списка.

Дополнительно `propertyDataFromListItem` задаёт району пустую строку, а detail-запрос отключён для объектов, уже находящихся в списке. Поэтому выбор объекта из загруженных вариантов очищает район; при прямом открытии страницы результат также зависит от того, успел ли отдельный detail-запрос выполниться до загрузки списка. Это потеря данных в форме, а не отсутствие района у объекта.

**Другие формы:** `/api/v1/properties/options/`, `/complexes/options/`, `/customers/options/` ограничивают справочники значением `PUBLIC_CATALOG_API_MAX_RESULTS` (по умолчанию 200). Интерфейс сообщает об ограничении и предлагает Django-форму, но не предоставляет удалённый поиск/следующую порцию и не гарантирует включение уже выбранного значения. В отличие от калькулятора, предел 200 в этой сверке установлен по коду; отдельная нагрузочная фикстура для каждого справочника не создавалась.

Источники: `frontend/src/pages/MortgageCalculatorPage.tsx:281`, `:419`, `:472`, `:1076`; `api_v1/views.py:2864`, `:3146`, `:3265`; `real_estate_investing/settings.py` (`PUBLIC_CATALOG_API_MAX_RESULTS`).

Исправление: ограниченный серверный поиск с догрузкой, гарантированное включение выбранных ID и загрузка района из detail-контракта. Простое снятие всех лимитов не требуется.

### F08. Нельзя экспортировать несохранённый расчёт

Django позволяет выгрузить Excel/Word непосредственно из обеих форм, включая расчёт без выбранного объекта. React предлагает выгрузки только из карточки уже сохранённого расчёта. На экране рассчитанной ипотеки ссылок Excel/Word — 0.

Поскольку сохранение в React требует авторизации и выбранного каталожного объекта, прежний сценарий «ввести условия → рассчитать → получить файл» утрачен, в том числе для ручного объекта F03.

Источники: `templates/mortgage/mortgage_form.html:534`, `:541`, `:748`, `:755`; `mortgage/views.py:1118`; `frontend/src/pages/MortgageCalculatorPage.tsx:931`; `frontend/src/pages/SavedMortgageCalculationDetailPage.tsx:145`.

Исправление: вернуть экспорт по валидированным параметрам без обязательного сохранения и с прежними правилами доступа. Экспорт сохранённых расчётов уже работает и проверен существующими браузерными тестами.

### F09. На экранах результата и сохранённого расчёта не хватает показателей

На Django-странице рыночного расчёта явно показаны процент и дата первого взноса, срок в месяцах, срок и ставка льготного периода, число льготных/основных платежей и долг после льготного периода. React-карточка сохранённого расчёта выводит только часть этих сведений через `MortgageResult`.

Потеряно явное представление:

- процента и даты первоначального взноса в сохранённой карточке;
- длительности и ставки льготного периода;
- числа платежей отдельно по льготному и основному периодам;
- суммы кредита после льготного периода;
- точного общего срока в месяцах при замене на компактное число лет;
- изображения планировки непосредственно в карточке/разворачиваемой строке расчёта.

Дата первого взноса и его процент отсутствуют также в сохранённой траншевой карточке. Часть значений можно вывести из графика или получить через «Новый по образцу», но это не заменяет прежний состав полей.

API уже содержит большинство исходных параметров; отдельные итоговые показатели (`loan_after_grace`, раздельные количества платежей) не представлены отдельными полями ответа. Значение `paymentsCount` в ответе есть, но компонент его не выводит.

Источники: `templates/mortgage/mortgage_detail.html:123`, `:174`; `templates/mortgage/trench_calculation_detail.html:122`; `frontend/src/features/mortgage/MortgageResult.tsx:49`; `frontend/src/pages/SavedMortgageCalculationDetailPage.tsx:223`; `frontend/src/pages/SavedTrenchMortgageCalculationDetailPage.tsx:241`; `api_v1/mortgage_service.py:133`.

Исправление: сверить состав карточек и результатов с прежними таблицами, вернуть перечисленные поля и единицы измерения. Показ первых 12 платежей сам по себе не является потерей: полный график доступен по кнопке.

### F10. Пропала переплата по отдельным траншам

В Django-таблицах результата и сохранённого расчёта есть колонка «Переплата, руб.». API передаёт `trenches[].overpayment`, но `TrenchMortgageResult` не выводит её. Общая переплата сохранена, детализация по траншам потеряна.

Источники: `templates/mortgage/mortgage_form.html:798`, `:812`; `templates/mortgage/trench_calculation_detail.html:173`; `api_v1/trench_mortgage_service.py:197`; `frontend/src/features/mortgage/TrenchMortgageResult.tsx:109`.

Исправление: вернуть отдельную денежную колонку. Переименование «Остаток долга» в «Остаток к выдаче» не считается ошибкой: используемое значение действительно равно ещё не выданной части кредита (`loan_amount - cumulative_amount`), а не текущему долгу после погашений.

### F11. Потеряны отдельные фильтры каталога объектов

Django предоставляет город, застройщика, ЖК, корпус, номер квартиры, планировку, площадь и стоимость. В React остались общий поиск и сортировка. Поиск по тексту не заменяет одновременное применение структурированных фильтров, особенно числовых.

API частично поддерживает идентификаторы города, застройщика, ЖК, корпуса и планировки, но элементы управления отсутствуют; отдельные фильтры площади и точной стоимости в новом query-сериализаторе также отсутствуют. В интерфейсе сортировки нет застройщика, корпуса, квартиры и планировки, хотя часть этих полей API сортировать умеет.

Источники: `templates/property/property_list.html:37–90`; `frontend/src/pages/PropertyListPage.tsx:11`, `:140`; `api_v1/serializers.py:3162`.

Исправление: вернуть прежний набор комбинируемых фильтров и сортировок, перенести значения в URL и проверить восстановление состояния при навигации.

### F12. Потеряны диапазонные фильтры историй и расчётов клиента

Общий Django-блок содержит город и пары «от/до» для стоимости, первого взноса, платежа, срока в годах и ставки. Он используется в историях и на странице клиента.

В React-историях есть текстовый поиск и сокращённый список сортировок; у клиента добавлен выбор типа программы, но прежних диапазонов и города нет. Соответствующие API query-сериализаторы тоже не принимают эти диапазоны. В интерфейсе рыночной истории нет сортировки по сроку, хотя API её поддерживает; в траншевой истории нет прежнего отбора/сортировки по последнему платежу.

Источники: `templates/mortgage/includes/calculation_filter_form.html:1`; `mortgage/utils.py:76`; `customer/views.py:603`; `frontend/src/pages/SavedMortgageCalculationListPage.tsx:23`; `frontend/src/pages/SavedTrenchMortgageCalculationListPage.tsx:23`; `frontend/src/features/customer/CustomerCalculationsSection.tsx:27`, `:83`; `api_v1/serializers.py:1742`, `:3989`, `:4026`.

Исправление: восстановить город, диапазоны, единицы срока и прежние поля сортировки во всех трёх представлениях; сохранить новый фильтр типа программы как дополнение.

### F13. Не перенесена синхронизация банков и их программ

В Django администратору доступны два разных действия: «Обновить данные банков» и «Обновить ипотечные программы». React-список банков не содержит их, API v1 не предоставляет соответствующих операций. Синхронизация ключевой ставки перенесена, но это другой процесс.

Источники: `templates/bank/catalog_form.html:41–56`; `bank/views.py:165`, `:184`; `frontend/src/pages/BankListPage.tsx:115`; `api_v1/urls.py`.

Исправление: перенести оба административных сценария с прежним разграничением прав, сводкой и предупреждениями. Обращение к внешнему источнику банков в рамках аудита не запускалось: проверено наличие/отсутствие функции, а не актуальность внешних данных.

### F14. Главная страница заменена другим рабочим сценарием

Django показывает активные ЖК выбранного города и переключение «Списком / На карте», фотографии, описание локации и ссылки на карты. React показывает общую статистику и несколько последних объектов недвижимости; выбор города и карта отсутствуют, query-параметры `city`/`view` не используются.

Это функциональная замена содержимого, а не только новый дизайн. Эквивалентный список ЖК частично доступен в другом разделе, но прежний сценарий карты не перенесён.

Источники: `homepage/views.py:15–68`; `templates/homepage/index.html:155`; `frontend/src/pages/HomePage.tsx:9`; `api_v1/views.py:594`.

Исправление: восстановить сценарий выбора города и карты либо отдельно принять изменение требований к главной странице. Работоспособность внешнего сервиса карт не проверялась; отсутствие самого React-сценария подтверждено.

## Прямое сравнение вычислений

Базовые условия: стоимость `5 000 000,00`, скидка 0%, взнос 20%, дата `01.10.2026`, срок 360 месяцев, ставка 15%. В каждой строке изменяются только указанные условия. Вычисления выполнялись через обе HTTP-точки, а не только вызовом общей функции.

| Сценарий | Условия | Строк графика | Отличия |
|---|---|---:|---:|
| Рыночная, базовая | Базовые условия | 360 | 0 |
| Скидка в процентах | 3,37% | 360 | 0 |
| Удорожание в рублях | 123 456,78 руб. | 360 | 0 |
| Взнос в рублях | 1 234 567,89 руб. | 360 | 0 |
| Льготный период | 12 месяцев под 6%, затем 15% | 360 | 0 |
| Неполное число лет / конец месяца | 13 месяцев, 31.01.2028 | 13 | 0 |
| Нулевой взнос | 0% | 360 | 0 |
| Полная оплата | Взнос 100% | 360 | 0 |
| Предельный срок | 600 месяцев | 600 | 0 |
| Один транш | Вся сумма одним траншем | 360 | 0 |
| Два транша | 30% под 1%; остаток через год под 15% | 360 | 0 |

| Разные ставки траншей | 90% под 30%; остаток через год под 1% | 360 | 0 |

Сравнение не является независимой финансовой экспертизой формул: обе версии используют общий `MortgageCalculator` и общие функции `trench_mortgage.views`. Оно проверяет, что API не меняет их результат при одинаковых исходных условиях. Исходный код рыночного API нормализует деньги отдельно, поэтому сценарии рублей/процентов включены специально.

Нулевая ставка рыночного кредита не объявляется поддержанным совпадающим сценарием: старая форма допускает 0, но общий аннуитетный код делит на ноль, тогда как API требует минимум 0,01%. Это ужесточение валидации предотвращает старую ошибку; его не следует трактовать как необходимость вернуть падение. В React основной input всё ещё имеет `min=0`, что расходится с API и требует согласования текста/границы поля.
