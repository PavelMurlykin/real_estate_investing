**Исходная проверка до исправлений**

Проверены работающие формы `http://localhost:18080/app/mortgage` и `http://localhost:18080/app/mortgage/trench`, а также Django-форма `/mortgage/?legacy=1`. Браузерная проверка выполнена в Chromium на Windows с шириной 360 и 1280 CSS px. Создание новых квартир и сохранение расчётов проверены дополнительно на отдельном PostgreSQL с синтетическими данными.

При одинаковых входных параметрах Django и API дали одинаковые результаты в **37 валидных сценариях и всех 13 143 строках графиков**. Независимая проверка аннуитетной формулы с Decimal и амортизации каждого транша выявила численные ошибки в пяти граничных рыночных сценариях. Все 12 проверенных траншевых сценариев прошли независимую числовую сверку.

Проверенный checkout — `6d9596eccc198bece9ac711c4248f67f60023da1`. На рабочем стенде загружается `app-C8dixIIj.js`, свежая сборка checkout — `app-DyZnVLQy.js`. SHA-256 файла React-калькулятора в контейнере начинается с `b7a2cfe2`, в checkout — с `f94c34b6`. Исходники общего калькулятора, сериализаторов API и траншевого расчёта побайтово совпадают с контейнером. Это позволяет отнести численные ошибки к текущему общему коду, а ошибку ожидания объекта — к более ранней сборке рабочего интерфейса.

1. **P1. Рыночный график перестаёт погашать основной долг на допустимой границе ставки и срока.**

   Ввести стоимость 5 000 000 ₽, взнос 20%, ставку 100%, срок 600 месяцев и дату 11.11.2026. API возвращает HTTP 200, кредит 4 000 000 ₽ и платёж 333 333,33 ₽. Во всех 600 строках погашение основного долга равно нулю. После последнего платежа остаток составляет 4 000 000 ₽. В сводке указана переплата 196 000 000 ₽, хотя сумма показанных процентов равна 199 999 998 ₽.

   При 100% на 360 месяцев сумма погашенного основного долга превышает кредит на 33,63 ₽. При 50% на 600 месяцев превышение составляет 8,58 ₽. Дополнительно обнаружены отклонения на верхней разрешённой стоимости 9 999 999 999 999,99 ₽, включая остаток 52,69 ₽ при ставке 0,01%.

   Причина связана с вычислением аннуитета и последовательным обновлением остатка в float. Для устранения требуется численно устойчивый расчёт и согласование последнего платежа с фактическим остатком. Ошибка присутствует в Django и API. [Коэффициент и график](../mortgage/mortgage_calculator.py#L7), [числовые результаты](../outputs/mortgage-audit-2026-11-11/calculations-live.json), [подтверждение в браузере](../outputs/mortgage-audit-2026-11-11/ui-high-rate.log).

2. **P1. Переполнение даты возвращает HTTP 500 в обоих калькуляторах.**

   Указать дату взноса `9999-12-31` и положительный срок. Для траншевой ипотеки оставить один транш с той же датой. Формат даты принимается, затем расчёт даты окончания вызывает `ValueError: year 10029 is out of range`. В React появляется общая ошибка без привязки к полю.

   Требуется проверять возможность построения даты окончания до вызова расчётного кода и возвращать ошибку поля с HTTP 400. Это воспроизведено на рабочем стенде и в текущих исходниках. [Валидация рыночных параметров](../api_v1/serializers.py#L3935), [построение даты траншевой ипотеки](../trench_mortgage/views.py#L448), [браузерные проверки](../outputs/mortgage-audit-2026-11-11/ui-live.json).

3. **P1. На рабочем стенде быстрый расчёт может опередить загрузку выбранного объекта.**

   При задержке ответов каталога и карточки объекта открыть ссылку `/app/mortgage?propertyId=14` и сразу рассчитать. Кнопка остаётся активной, в запрос попадает цена по умолчанию 5 000 000 ₽ вместо цены выбранной квартиры 16 409 971 ₽. После загрузки объекта результат помечается устаревшим.

   Естественный переход из карточки передаёт также `propertyCost=16409971.00`, поэтому исходная цена сохраняется. Однако поздняя подстановка остальных сведений об объекте также делает результат устаревшим. В текущем checkout ожидание загрузки объекта уже реализовано. Для рабочего стенда требуется обновление обслуживаемой сборки с последующей проверкой этого сценария. [Доказательство обоих вариантов ссылки](../outputs/mortgage-audit-2026-11-11/ui-live.json).

4. **P2. Начальное состояние траншевого калькулятора изменилось после перехода на React.**

   Django начинает с одного транша и заполненной датой. После ввода стоимости быстрый расчёт выполняется. React начинает с двух траншей, дата второго пустая. Нажатие кнопки в начальном состоянии возвращает HTTP 400 с сообщением «Неправильный формат date. Используйте один из этих форматов: YYYY-MM-DD.». Для быстрого расчёта нужно выбрать один транш или заполнить вторую дату.

   Следует определить единое начальное состояние и показывать понятное сообщение о дате конкретного транша. [Начальное количество траншей](../frontend/src/pages/MortgageCalculatorPage.tsx#L230), [браузерные наблюдения](../outputs/mortgage-audit-2026-11-11/ui-live.json).

5. **P2. Различается преобразование дробного срока в годах.**

   Ввести `12.5` в поле срока в годах. Django преобразует его в 144 месяца, React — в 150 месяцев. Срок 25 месяцев отображается в React как 2,08 года, при этом сам запрос сохраняет 25 месяцев.

   Это изменение правил взаимодействия полей. Требуется определить ожидаемое поведение дробных лет для функционального паритета. [Синхронизация React](../frontend/src/pages/MortgageCalculatorPage.tsx#L835), [синхронизация Django](../static/js/mortgage_form.js#L1806), [наблюдения в браузере](../outputs/mortgage-audit-2026-11-11/ui-live.json).

Валидация API местами строже Django. Старый рыночный обработчик принимает некоторые наборы с нулевой или отрицательной ценой, скидкой 100% и взносом в рублях выше цены, которые API отклоняет. Ставка выше 100% также допускается старой формой и ограничивается API. Это отдельные различия правил, которые следует учитывать при определении ожидаемого паритета. При очистке даты React подставляет текущую дату, тогда как прямой API-запрос с пустой датой отклоняется.

В изолированном стенде модератор создал новую квартиру, сохранил расчёт и выгрузил Excel и Word в обоих режимах. Набор backend-тестов дополнительно проверяет запрет создания для обычного пользователя, повторное использование квартиры и атомарность записи.
